## 当前唯一未解问题（优先处理）：`pmatmul` 的 `cublasSgemm` 100000

**症状**：pmatmul 编译/链接 OK，运行报 `cublasSgemm failed: 100000`（= `ACL_ERROR_INVALID_PARAM`）。
**已确认的根因层级**（2026-08-21 真机证据）：
1. 真机 `acl_cblas.h` 里**没有 fp32 的 `aclblasSgemm`**（grep 无）；
2. `aclblasGemmEx` 的**数据类型组合受限**：仅 `fp16×fp16×fp16`、`fp16×fp16×float`、
   `int8×int8×float`、`int8×int8×int32`——**没有 fp32×fp32×fp32**；
3. 于是 `wcublasSgemm`（`src/bridge/blas/src/cublas_v2_wrapper.cpp`，现已被改成
   **fp32 输入降级 fp16 计算**、C 保持 fp32=`fp16×fp16→fp32` 组合，见 commit `3a67cd5`）
   应该在输入降级后不再触发 fp32 类型错误；
4. **但仍报 100000**（最新一轮 `e30df4c` 真机复测）→ 说明 100000 已不是"类型组合"，
   而是下一个层次的问题。候选（按嫌疑排序）：
   - **shape/维度约束**：昇腾 GemmEx 在 AIC 上对 m/n/k 有对齐要求（如 16 的倍数，
     某些核要求 ≥ 某下限）；当前 16×16×16 可能不满足 → 试 **32×32×32** 或 64；
   - **stream 相关**：`cublasSetStream(handle, stream)` 传的是 host 创建的 stream，
     `wcublasSgemm` 会自建 stream 兜底也可能埋雷 → 在 `gemm_impl` 打日志看
     `handle->stream` 实际是什么、`aclGetRecentErrMsg()` 到底报啥；
   - **aclComputeType**：`gemm_impl` 用 `ACL_COMPUTE_HIGH_PRECISION`，fp16 组合下
     可能需要 `ACL_COMPUTE_LOW_PRECISION` 或其他值（真机头查 `ACL_COMPUTE_*` 枚举）；
   - **C 布局/初始化**：昇腾不清零，`cudaMemset(dC,0,...)` 已做；C 是 `float*`、ldc=M=16，
     先保持原样。

**建议的动作顺序**（每步只改一处，push + server_cmd，真机复测）：
1. `gemm_impl`/`wcublasSgemm` 里加详细日志：打印 `handle->stream` 是否非空、转换后的
   `ACL_FLOAT16`/`lda/ldb/ldc`、`aclGetRecentErrMsg()` 的最近错误信息；
2. 把 pmatmul 的 M/N/K 从 16 改 **32**（A/B/C 都是 32 的倍数），验证 shape 假设；
3. 查真机头 `ACL_COMPUTE_*`，把 `ACL_COMPUTE_HIGH_PRECISION` 换成 fp16 组合正确的值；
4. 若都不是，可走原生 `aclblasHgemm`（fp16×fp16×fp16）做**纯 fp16 对照**：由 wrapper 把
   fp32 输入转 fp16 存 device，调 `aclblasHgemm` 用 fp16 C——但这会改变返回结果精度
   （fp32 C 输出变 fp16），与 CUDA `cublasSgemm` 语义不同，只能作为"昇腾能算 gemm"的证明，
   不能作 fp32 兼容最终形态。届时把"昇腾只有 fp16/int8 gemm"写进文档。

**已知历史教训（别再踩）**：
- 100000 曾在 cublasMatmul 冻结 5 轮：null stream → auto-create、显式 stream、4×4→16×16、
  aclGetRecentErrMsg 全试过，都被"类型组合"卡住——现在类型这层已解，剩的是上述候选。
- `wcublasSgemm` 的旧实现直接 `ACL_FLOAT` 调 GemmEx（已成历史，别回退）。
