## 建议的新开发方向（按优先级，选一个做深；每项都有 verify 方式）

### 方向 1（推荐）：kernel_convert.py 增强 —— 从 `<<<>>>` 提取真实 blockDim
- 现状：`VF_THREADS = "cce::dim3{256, 1, 1}"` 硬编码；`convert_launch_config` 已能把
  `<<<grid, block, shared, stream>>>` 改成昇腾 3 参，但 **VF 函数的启动线程数仍是写死的 256**。
- 改法：解析每个 kernel 对应的 `<<<g, b, ...>>>` 里的 `b`，生成 `cce::dim3{b.x, b.y, b.z}`
  传给 `async_invoke`；支持 `b` 是常量/简单整型表达式；无启动配置时 fallback 256。
- verify：把 vectorAdd/minimal 改 `<<<blocks, 512>>>`（或 128/1024），
  kernel 转换后的 `.cce` 里 `async_invoke<cce::dim3{512,1,1}>`，真机 `run_tests.sh all` 仍 8/8。
- 顺手：`convert_launch_config` 里 `sharedMem≠0` 的 WARN 目前丢弃，可在注释里说明昇腾语义。

### 方向 2：多 kernel/多文件 + reduction 或 atomic kernel 真机验证
- 现状：只验证了单个 elementwise kernel（vectorAdd/addOne）。
- 做：写一个含 `__syncthreads`（→asc_syncthreads）+ `__shared__`（→__ubuf__）的 reduction
  或 histogram（atomicAdd）kernel；确认 SIMT 适配宏表（simt_adaptor.h）在真机能编译运行。
- verify：新示例真机跑通 + 数值正确；把`待确认 #6（原子操作地址空间）`从 ⚠️ 关掉。
- 这是 `docs/03_Comparison/CURRENT_STATE.md` 的显式待确认项，价值高。

### 方向 3：cublas 桥真机验证（aclblasGemmEx）
- 现状：`cublas_v2_wrapper.cpp` 已实现 gemm/gemv 映射（自定义 handle → 直接传 stream），
  但**从未真机运行验证过**；且 wrapper 链接了 `libacl_cblas.so`（运行期解析，
  `nm -D` 可见未定义符号）。
- 做：写一个调 `cublasSgemm` 的小示例，真机跑通并校验 C=A×B。
- verify：示例数值校验通过；顺带确认 libacl_cblas 依赖是否需要在链接期处理。
- 注意：CUDA 内存默认清 0 但昇腾不清（CLAUDE.md 已知差异），gemm 前记得自己初始化 C。

## 已知薄弱点（接手时心里有数）

1. **kernel 转换器是正则**（167 行）：不支持嵌套括号参数、模板 kernel、函数指针、
   多 kernel 时 blockDim 硬编码 256。块注释/字符串里的伪 `<<<>>>` 可能误伤。
2. **host 桥是"骨架+少量真机验证"**：124 个 wcuda 声明里，只有
   GetDeviceCount/SetDevice/GetDevice/Malloc/Memcpy/Memset/StreamCreate/CreateContext 等
   核心路径在 8/8 覆盖；Graph/Texture/Symbol/Peer/Unified/SOMA 等**多数从未真机跑过**
   （要么 not-support 占位、要么未经运行验证）。
3. **ccec+glibc 2.39 兼容是"遮蔽头 + 宏替换"**：脆弱。新加宿主代码/头文件时可能撞
   `_Float32`/`__FILE` 之类，改影子头要回归 8/8。
4. **wcudaMalloc 的 107002 修复只覆盖了有源码路径的入口**：其他 `wcuda*` 里若出现
   "原生调用在 WCUDA_RETURN 之前"的写法仍会踩（已审计过 4 处，但新代码要守规矩）。
5. **.gitignore 现在很全**，但 `diag/` 探针若被常态化使用，建议把它们的二进制/产物
   明确忽略（当前已做）。
